System Description

Windsage is a webhook-driven service that receives artifact commit notifications from Gitea repositories, persists them to a PostgreSQL database, and notifies downstream systems (Windstorm) of changes. The system is designed to run in a Kubernetes environment using Argo Events for event-driven pod creation.

Key Features

  • Webhook endpoint for Gitea push events
  • Automatic artifact repository tracking
  • Commit history persistence in PostgreSQL
  • Default branch filtering
  • Downstream notification via Windstorm webhook
  • Event-driven Kubernetes deployment

Physical Architecture

System Context Diagram

Component Breakdown

1. Gitea (External)
Type: External System
Purpose: Git repository hosting platform that triggers webhooks on push events
Interface: HTTP POST webhook to Windsage endpoint
2. Argo Events EventSource
Type: Kubernetes Custom Resource
Purpose: Exposes webhook endpoint and receives HTTP POST requests
Configuration:
  • Endpoint: /windsage
  • Port: 12000
  • Method: POST
3. Argo Events Sensor
Type: Kubernetes Custom Resource
Purpose: Triggers Kubernetes Pod creation upon webhook event
Behavior:
  • Extracts webhook payload fields
  • Creates ephemeral Windsage pod with parameters
  • Passes extracted data as CLI arguments
4. Windsage Pod
Type: Kubernetes Pod (Event-driven, ephemeral)
Image: westfallio/windsage:v0.1.5
Purpose: Process webhook event and update database
Components:
  • Python 3.11 runtime
  • SQLAlchemy ORM
  • Fire CLI framework
  • Requests HTTP client
Lifecycle: Created per webhook event, terminates after processing
5. PostgreSQL Database
Type: Persistent Data Store
Deployment: Kubernetes StatefulSet (postgres-postgresql.windstorm:5432)
Schema:
  • artifacts table: Tracked repositories
  • artifact_commits table: Commit history
6. Kubernetes Secrets
Type: Kubernetes Secret Resource
Secret Name: dbparams
Contents:
  • username: Database username
  • password: Database password
  • table: Database name
7. Windstorm (External)
Type: External System
Purpose: Downstream event handler/workflow system
Interface: Webhook endpoint receiving artifact update notifications
URL: http://windstorm-webhook-eventsource-svc.argo-events:12000/windstorm

Data Flow

  1. Developer pushes code to Gitea repository
  2. Gitea sends webhook POST to Argo Events EventSource
  3. EventSource triggers Sensor with webhook payload
  4. Sensor creates Windsage Pod with extracted parameters
  5. Pod loads database credentials from Kubernetes Secret
  6. Pod connects to PostgreSQL and stores/updates artifact data
  7. Pod sends notification to Windstorm webhook
  8. Pod terminates successfully

Functional Architecture

Activity Flow Diagram

Functional Modules

<<module>> Event Reception
Responsibility: Receive and validate webhook payloads
Inputs: HTTP POST request with Gitea webhook JSON
Outputs: Parsed webhook event data
Functions:
  • Accept POST requests on /windsage endpoint
  • Validate webhook structure
  • Extract required fields (ref, commit, full_name, etc.)
<<module>> Event Processing
Responsibility: Coordinate workflow execution
Inputs: Webhook event parameters
Outputs: Processing status
Functions:
  • Parse ref string (refs/heads/branch → branch)
  • Filter non-default branches
  • Orchestrate database operations
  • Handle error conditions
<<module>> Database Management
Responsibility: Persist artifact and commit data
Inputs: Artifact metadata, commit information
Outputs: Database transaction results
Functions:
  • Establish PostgreSQL connection with credentials
  • Query existing artifacts by full_name
  • Insert new artifact records
  • Update default branch if changed
  • Check for duplicate commits
  • Insert commit records with timestamps
  • Close connections and cleanup
<<module>> Notification Service
Responsibility: Notify downstream systems
Inputs: Artifact ID
Outputs: HTTP response status
Functions:
  • Construct notification payload
  • POST to Windstorm webhook endpoint
  • Handle connection errors gracefully

Deployment Workflow

Step 1: Initial Setup
  1. Create namespace: kubectl create namespace argo-events
  2. Install Argo Events: kubectl apply -f argo-events.yaml
  3. Create ServiceAccount with Pod creation permissions
  4. Create Kubernetes Secret with database credentials
Step 2: Deploy Windsage Components
  1. Apply EventSource: kubectl apply -f event-source.yaml
  2. Apply Sensor: kubectl apply -f sensor.yaml
  3. Verify EventSource service is running and accessible
Step 3: Configure Gitea Webhook
  1. Navigate to repository settings in Gitea
  2. Add webhook with URL: http://<eventsource-service>:12000/windsage
  3. Set content type to application/json
  4. Select "Push events" as trigger
Step 4: Runtime Operations
  1. Developer pushes code to Gitea
  2. Gitea triggers webhook to EventSource
  3. Sensor creates ephemeral Windsage pod
  4. Pod processes event and updates database
  5. Pod notifies Windstorm and terminates

⚠️ Operational Considerations
  • Database Connection Pooling: Each pod creates a new connection; consider connection limits
  • Error Handling: Windstorm notification failures are logged but non-fatal
  • Pod Cleanup: Failed pods remain for debugging; implement cleanup policy
  • Secret Rotation: Database credentials should be rotated periodically
  • Version Management: Container images are tagged; update Sensor when deploying new versions
